## Rendering model

**Everything is static.** `npm run build` prerenders all 121 pages to HTML at build time.
Only the four `/api/*` routes are dynamic (`ƒ` in the build output); every page is `○`.

This was a deliberate change — the site previously carried `export const dynamic =
'force-dynamic'` in the root layout, forcing a server render on every request for pages
with no per-request data. If you find yourself adding `force-dynamic`, `headers()`, or
`cookies()` to a page, stop: it will opt that route out of static generation. There is no
per-request data on this site.

Content changes require a rebuild and redeploy. That is the tradeoff for a site that
serves instantly from the edge.

## Content model

There is **no CMS**. Copy lives as TypeScript objects inside each `page.tsx` — FAQ arrays,
feature lists, comparison rows, deployment phases. Editing content means editing React.

Historically most pages were generated by one-shot scripts, which is why pages within a
silo are structurally identical and differ only in copy. Those generator scripts have been
removed; pages are now maintained by hand from the templates in
[`ADDING-PAGES.md`](ADDING-PAGES.md).

**If content volume grows substantially**, the natural next step is MDX or a headless CMS.
Do not attempt that incrementally — it is a deliberate migration, and half-migrated
content is worse than either end state.

## Data layer

Prisma + PostgreSQL, used **only** to capture leads. Four tables, all write-only:

| Table | Written by |
|---|---|
| `DemoRequest` | `POST /api/book-demo` |
| `ContactSubmission` | `POST /api/contact` |
| `FreeTrialRequest` | `POST /api/free-trial` |
| `NewsletterSubscription` | `POST /api/newsletter` (no UI currently posts to this) |

Nothing in the site reads from the database, and nothing is notified when a lead arrives.
Each route validates, writes the row, and returns. **Leads must be read out of the
database manually** — there is no email or alert.

An Abacus.AI notification-email integration previously ran here; it was removed along with
its five environment variables when the project moved to Vercel. If a notification channel
is added back, it must stay non-fatal: a failed notification must never lose a lead that
has already been written.

`lib/prisma.ts` is the singleton client. Do not instantiate `PrismaClient` anywhere else.

## Component layers

| Layer | Rule |
|---|---|
| `ui/` | Unstyled-ish primitives. Add with `npx shadcn@latest add <name>`. Do not put product logic here. |
| `system/` | Cross-cutting infrastructure. Theming, SSR safety, JSON-LD, form submission. |
| `layout/` | Site chrome and the page scaffold. Changing these affects all 121 pages. |
| `content/` | Reusable content blocks composed by pages. **Most new components go here.** |
| `motion/` | Presentation pieces with animation. All respect `prefers-reduced-motion`. |
| `mockups/` | Faux product UI. GSAP + ScrollTrigger via `useDeferredGsap`. |

`PageShell` (`layout/page-shell.tsx`) is the important one — it renders breadcrumbs, emits
page-level structured data, and appends the CTA band. Nearly every page goes through it.

## SSR and hydration safety

`eslint.ssr.config.mjs` is a hand-written ESLint plugin that runs after every build. It
fails the build on the patterns that cause most Next.js hydration errors:

- `window` / `document` / `localStorage` at module scope
- `useState(Date.now())`, `Math.random()` in render
- `toLocaleString`-family calls without an explicit locale (and `timeZone` for dates)

**Do not weaken it.** Fix the flagged code using the primitives in `components/system/`:
`ClientOnly`, `useMounted`, `SafeDate`, `SafeTime`, `SafeNumber`. If a value is genuinely
build-time-constant, hoist it to module scope with a comment explaining why (see
`COPYRIGHT_YEAR` in `components/layout/site-footer.tsx`).

The codebase also uses defensive optional chaining throughout (`item?.label ?? ''`). That
is an established convention here — match it in code you touch.

## Design tokens

All color, spacing, radius, shadow and timing values are CSS variables in
`app/globals.css`, surfaced to Tailwind through `tailwind.config.ts`. Full reference in
[`DESIGN-SYSTEM.md`](DESIGN-SYSTEM.md).

Two things that will trip you up:

- **Opacity stops `15` and `25` are declared explicitly** in `tailwind.config.ts`. They are
  not Tailwind defaults. Without them, `bg-live/15` silently generates no CSS at all and
  the element renders with a transparent background.
- **`--live`, `--warn`, `--critical` have different values per theme.** Light-theme values
  are darkened to clear WCAG AA on a near-white background.

## Build and deploy

```bash
npm run build     # → .next/, all pages prerendered
npm start         # serve the production build
```

`next.config.js` notes:
- `images.unoptimized: true` — deliberate for the deploy target. Images still use
  `next/image` with explicit dimensions to prevent layout shift.
- `eslint.ignoreDuringBuilds: true` — but `typescript.ignoreBuildErrors: false`, so type
  errors *do* fail the build.
- The webpack block only customizes chunk filenames. The standalone-mode Abacus client
  error reporter that used to live here was removed with the rest of the integration.

Deploy target is Vercel-compatible. `.vercelignore` excludes env files and build info.
